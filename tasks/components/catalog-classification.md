## Public query contract (proposed for coordination)

Add a public catalog endpoint distinct from private `/api/v1/hotels`: proposed `GET /api/v1/public/hotels`. Only approved published listing facts may appear. This is a future contract, not an available endpoint; existing publication/booking readiness gates are not relaxed by this proposal.

Canonical metadata parameters:

- `q`: trimmed text, 1–100 characters if supplied; literal case-insensitive substring on public hotel name and destination name (not private contacts). Escape wildcard characters so percent/underscore do not broaden the match.
- `destination`: one canonical destination slug; resolve reviewed legacy slug to canonical URL.
- `region`: optional allowlisted geographic browse key, initially `north-east` only if PO approves its district membership; expands to those property district codes and combines with other filters using AND.
- `district`: one approved district code. It combines with destination using AND; conflicting combinations produce zero results rather than silently dropping one filter.
- `property_types[]`, `themes[]`: distinct allowlisted keys, bounded to vocabulary size. OR within either group, AND across groups. The UI must state “matches any selected theme”.
- `amenities[]`: later, only promoted/reviewed amenities; require ALL selected amenities. Hide capability until that publication path exists. Never infer amenities from themes/location.
- `min_stars`: integer 1–5; matches reviewed sourced classification >= threshold. Null/unverified/expired classifications are excluded when filtering, retained in unfiltered discovery.
- `sort`: `name` or `editorial` initially; name ascending with hotel ID tie-break, editorial_rank ascending/nulls last then name/ID. Default proposal: editorial only once ranks actually exist, otherwise name. Use one fixed collation/normalization consistently so paging is stable.
- `page`: positive integer; page size 24, bounded fixed server-side. Return true total and empty data for an out-of-range page; do not silently clamp the URL to another page.

Invalid enum/range/duplicate scalar inputs return Laravel-style 422 validation errors; unknown taxonomy IDs/slugs return a recoverable filter error rather than becoming an unrestricted query. Inactive or removed values also require explicit recovery. Tracking parameters are handled separately from filter input and never affect selection. Do not return another category's results after quietly ignoring a bad value.

Response: `{data: HotelCard[], links, meta:{total,current_page,per_page,applied_filters,capabilities}}`, using Laravel pagination conventions. Card includes stable ID/public slug/name, reviewed property type, destination, district, themes, nullable sourced star classification and approved public photo. It excludes contact details, access membership, source-review notes and unpublished draft fields. `capabilities` explicitly lists available filters/sorts and `availability_search:false` until supported. Do not put an indicative rate in a field called price/total.

For smallest first increment, ship vocabulary + applied filters and total only; defer dynamic facet counts. If counts are later shown, calculate before pagination with all other filters applied (exclude the facet's own selection), count distinct hotels and document the same OR/AND semantics. Do not count only currently rendered cards. Public task owns accessible filter controls, URL/Back/refresh behavior, applied chips, clear actions, page reset on filter/sort changes, and modal Cancel discarding unapplied edits.

## Dates, guests and prices: explicit dependency gate

Metadata discovery does not validate a stay. Until dated stock/quote resolution exists, expose availability_search:false and do not offer “available on these dates”, actual-price ranges or price sorting. If unsupported booking parameters are submitted to the API, return 422 `availability_search_unavailable` rather than accepting and ignoring them. The UI may preserve dates as unverified trip context only with visible wording and without styling those values as applied availability filters.

Later availability mode requires check_in/check_out together, 1–30 hotel-local nights, quantity exactly 1, adults fitting the selected room and children exactly zero in the first booking scope. Reject unsupported child pricing explicitly. Every candidate plan must satisfy each night's inventory/restrictions/freshness/ownership checks. PMS failure/unknown is not available manual stock. Search remains advisory; booking-time hold validation remains required.

Use the cheapest eligible plan for the exact same stay/occupancy to represent a hotel's comparable total. Compute `stay_total_minor = sum(base_minor + tax_minor + fee_minor)` for all nights with strict mandatory_charges_complete=true. LKR integer minor units only; no arbitrary FX conversion. Min/max prices and price sort must use that full-stay total (label “Total for N nights, including mandatory charges”), not an undated/nightly legacy minimum. Tie-break by name/ID. Exclude unpriced/incomplete candidates from price/availability results; never substitute zero. Unsupported stay-level fees block a quote until a lossless allocation rule is agreed. Returned price needs stay/currency/occupancy context and as-of information. No independently mutable duplicate total column.

Archive compatibility must be handled once at the public URL boundary: `dest -> destination`, known legacy destination aliases -> canonical slug, `star -> min_stars`, `popular -> editorial` with honest label. Existing `category` values map only after taxonomy agreement: retain six stable experience keys (`beach`, `hills`, `wild`, `culture`, `adventure`, `city`) as themes; propose `north -> region=north-east`. Do not map any category into property_type. Do not translate old `min/max` nightly rupee limits into new stay-total minor limits without user review; show a recoverable message explaining changed price semantics. `in/out` can become unverified trip dates until availability support exists; they must not silently constrain a pretend result set. Public owner must inventory actual indexed URLs before redirect/canonical rules are finalized.

## Planner and personal-map boundaries

Expose destination IDs/slugs and reviewed hotel metadata as discovery building blocks; a destination without hotels is valid for planning. A planner selection stores a stable hotel/plan reference when actually chosen, not a mutable name or cheapest-card assumption. Per-stop dates are needed before cost/availability comparison; unknown total remains unknown. A request-quote planner and atomic multi-stop checkout are different scopes; neither is inferred here. Traveller accounts/map privacy, visited/want-to-visit records and sharing/import rules belong to their own ownership contract, never hotel staff membership. Use shared district codes so map/filter labels agree, without claiming a district was fully explored.
